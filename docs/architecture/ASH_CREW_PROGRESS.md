## Gate 1 supervised-process admission slice (2026-10-27)

- Scope: `SandboxManager.run_supervised_process()` in `src/ash/sandbox/manager.py` provides a one-shot process launch seam using Ash's existing Docker backend. Admission requires the selected backend to be Docker, nonzero CPU and memory limits (plus Docker's existing pids limit of 256), network disabled, a read-only workspace bind with nested mounts excluded, a workspace root, and scoped fallback disabled. It has no caller-supplied environment, passthrough variables, or stream callback, and closes child stdin. Docker fails the launch if it cannot exclude nested mounts. The existing `run()` path continues to own executable resolution, timeout handling, and process-tree cleanup.
- Timeout/cancellation handling: `DockerSandbox.wrap()` tags each container with a random per-run ownership label and uses a validated container name. A timeout, nonzero result, cancellation, startup error, output truncation, or ambiguous outcome triggers cleanup only after inspection confirms that label; removal targets the resulting container ID. Launch captures and pins one local Docker socket in the CLI environment, which is reused for cleanup so a concurrent active-context change cannot redirect removal. Cleanup is shielded until completion, then pending cancellation is propagated with cleanup failures attached. If the parent process is killed or crashes before cleanup runs, the daemon can still retain a live container; this slice does not prove crash-safe worker supervision.
- Backend decision: Docker is required because this seam requires aggregate CPU/memory and process-count limits. Bubblewrap lacks those limits. macOS `sandbox-exec` does not isolate host file reads. Auto-selected scoped execution and explicit fallback are rejected before child dispatch. No new sandbox stack was introduced.
- Boundary assessment: this invocation requires a local Unix socket or Windows named pipe endpoint, rejects explicit `DOCKER_HOST`/`DOCKER_CONTEXT` overrides and remote endpoints, pins the inspected socket for launch and cleanup, mounts only the configured workspace, excludes nested host mounts, does not mount host home/keychains or pass the host environment, and leaves only isolated loopback under Docker `--network=none`; external IP and cloud metadata access are therefore blocked if the local daemon enforces that network namespace. The supervised path also refuses ambient proxy variables and Docker client `config.json` proxy injection, and overrides proxy variables in the image with empty values. These controls were not daemon-verified here. A Unix-domain socket present under the mounted workspace remains reachable, and workspace contents remain visible, including embedded credentials or hard-linked host content. The API launches arbitrary commands and does not itself load Ash SDK/extensions, but a future worker command could load code from its image or mounted workspace. A Coworker supervisor must supply a controlled image and dedicated staged workspace that excludes host IPC and sensitive inputs before using this seam. Environment scrubbing and this process primitive do not authorize a coworker Ash runtime.
- Red/green evidence: before the entry point existed, the baseline reproduction selected scoped execution when Docker, Bubblewrap, and sandbox-exec were unavailable and launched a synthetic child through generic `run()`. After the change, the new supervised call refuses before spawning under the same condition.
